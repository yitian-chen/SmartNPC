# 技术实现方案 —— UE + MCP 中间层 + Hermes Agent

> 目标：在已用 UE 搭好的三维园区里，给 5 个人形机器人 NPC 各接入一个 Hermes Agent，复刻斯坦福小镇的"感知-记忆-反思-规划-行动"自运转效果。

---

## 一、核心架构：三层职责划分

先厘清一个**关键事实**（决定整个方案的走向）：

> **Hermes Agent 本身是 MCP 客户端（Client），不是 Server。**
> 它启动时会读取 `~/.hermes/config.yaml` 里的 `mcp_servers` 配置，**主动连接你提供的 MCP Server**，把 Server 暴露的工具（tools）注册成自己能调用的能力。

所以架构里"NPC 的眼睛和手"要由**你写的 MCP Server** 来提供，而不是让 UE 直接连 Hermes。

```
┌─────────────────────────────────────────────────────────────┐
│                      UE 游戏进程（世界模拟层）                  │
│  地图 / 角色建模 / 物理 / 导航 / 动画 / 交互物体                 │
│                                                              │
│  ┌────────────────────────────────────────────────────┐    │
│  │  Agent Bridge 子系统（UE 内，C++/蓝图）              │    │
│  │  · 采集每个 NPC 的感知快照                            │    │
│  │  · 接收行动指令并驱动 NPC 执行                        │    │
│  │  · 通过 HTTP/WebSocket 与 MCP Server 通信            │    │
│  └───────────────────┬────────────────────────────────┘    │
└──────────────────────┼──────────────────────────────────────┘
                       │ HTTP / WebSocket（本地 loopback）
                       ▼
┌─────────────────────────────────────────────────────────────┐
│                   MCP 中间层（你要新写的服务）                  │
│  · 对 Hermes 暴露标准 MCP 工具（perceive / move / speak…）    │
│  · 维护世界状态镜像、NPC 编号路由、事件队列                    │
│  · 对上：MCP Server（被 Hermes 连接）                        │
│  · 对下：UE Bridge 客户端（读写 UE 世界）                    │
└──────────────────────┬──────────────────────────────────────┘
                       │ MCP 协议（stdio 或 HTTP）
                       ▼
┌─────────────────────────────────────────────────────────────┐
│              Hermes Agent × 5（认知核心层）                    │
│  每个 NPC 一个独立实例：记忆流 + 反思 + 规划 + LLM 决策        │
│  · 辛博 / 柚子 / 老铆 / 微光 / 哨                             │
│  · 各自的 MEMORY.md、USER.md、技能库                         │
└─────────────────────────────────────────────────────────────┘
```

## 二、UE 层需要做什么

UE 是**世界模拟器**，负责"物理世界"的一切，并为每个 NPC 提供感知输入、执行行动输出。

### 2.1 场景与角色（已有）
- 地图（仓库 / 修理厂 / 休息区 / 充电区）
- 5 个人形机器人角色建模
- 需要补充：为每个可交互物体、每个区域、每个 NPC 打上**语义标签与唯一 ID**（如 `zone.repair_bay`、`obj.charging_pod_02`、`npc.AH-03`），因为 Agent 只能理解文本，不认识网格坐标。

### 2.2 感知系统（Perception）—— NPC 的"眼睛和耳朵"
为每个 NPC 周期性生成一份**文本化感知快照**，这是斯坦福小镇"局部感知"的关键（Agent 只知道自己视野范围内的事）：

- **视觉感知**：用 `USphereComponent` / `AIPerceptionComponent` 检测视野半径内的对象，输出为文本，例如：
  ```
  你（柚子）当前在【仓库】。
  可见：辛博正在3号货架清点物资；一台运输托盘停在门口；东侧通往修理厂的门开着。
  可交互物体：货架A(可存取)、旧留声机(可播放)、终端机(可查询库存)。
  ```
- **听觉/对话感知**：附近 NPC 的说话内容进入感知快照（带方向和距离衰减）
- **状态感知**：自身电量、机体损耗、当前手上的任务
- **采样频率**：不必逐帧，建议 1~5 秒一次快照或"事件驱动"（有新事件才推送），避免 LLM 调用爆炸和成本失控

### 2.3 行动系统（Action）—— NPC 的"手和脚"
接收 MCP 层下发的**结构化行动指令**，翻译成 UE 内的行为：

| 行动指令 | UE 实现 |
|---|---|
| `move_to(target)` | 用 NavMesh 寻路走到目标区域/物体 |
| `interact(object, verb)` | 播放对应交互动画 + 改变物体状态（如充电、维修、取货） |
| `speak(text, to?)` | 头顶气泡/字幕 + 触发听觉感知半径内其他 NPC |
| `pick_up / put_down(item)` | 附加/分离物体到手部插槽 |
| `emote(type)` | 播放情绪动画（挥手、点头、"发呆") |
| `wait(seconds)` | 待机 |

### 2.4 Agent Bridge 子系统（UE 内新增模块）
这是 UE 与 MCP 层的通信桥，建议用 C++ 写一个 `UGameInstanceSubsystem`：

- **上行**：把感知快照打包成 JSON，通过 HTTP POST / WebSocket 推给 MCP 层
- **下行**：监听 MCP 层的行动指令，路由到对应 NPC 的行为树/状态机执行，并回传执行结果（成功/失败/被打断）
- **世界时钟**：提供统一的"游戏内时间"，供 Agent 做日程规划（对应斯坦福小镇的"一天"）
- **通信方式选型**：推荐 UE 内置的 `FHttpModule` 或 WebSocket 插件；本地 loopback 通信延迟可忽略

### 2.5 UE 层不做什么
- **不做记忆、不做决策、不调 LLM**。UE 只负责"发生了什么"和"执行什么"，"想什么"全部交给 Hermes。这条边界一定要守住，否则逻辑会散落到两边难以维护。

## 三、MCP 层需要做什么

MCP 中间层是**你需要新写的核心服务**（Python 最合适，MCP 官方 SDK 完善）。它一身两职：

- **对上**：作为 **MCP Server**，被 5 个 Hermes Agent 连接，暴露标准 MCP 工具
- **对下**：作为 **UE Bridge 的客户端/服务端**，读写 UE 世界状态

### 3.1 对 Hermes 暴露的 MCP 工具（Tools）
这是 Agent 唯一能"感知世界"和"改变世界"的通道。建议设计成以下工具集：

```python
# 感知类（Agent 主动拉取，或由系统推送）
perceive()                       # 返回当前 NPC 的文本感知快照
get_self_status()                # 电量、损耗、当前任务、所在位置
look_at(target_id)              # 聚焦观察某个对象，返回细节描述

# 行动类（Agent 输出决策 → UE 执行）
move_to(target_id)              # 移动到某区域或物体
interact(object_id, verb)       # 与物体交互（充电/维修/取货/播放…）
speak(text, to_npc_id=None)     # 说话，可指定对象或对空气自言自语
pick_up(item_id) / put_down()   # 拿起/放下物品
emote(emotion)                  # 播放情绪动作

# 协作类（NPC 之间）
send_message(to_npc_id, text)   # 给指定 NPC 传话（即使不在视野内，模拟"托狗带话"式的异步沟通）
```

> **关键设计**：每个 Hermes 实例连接时要带上自己的 **NPC 身份标识**（通过不同的 MCP Server 端口/URL 或 header 区分），MCP 层据此把工具调用路由到正确的 NPC。

### 3.2 两种接入方式（对应 Hermes 的 mcp_servers 配置）

**方式 A：HTTP MCP Server（推荐，多 Agent 场景更清晰）**

每个 NPC 对应一个 URL 路径，5 个 Hermes 各自配置：
```yaml
# 柚子的 ~/.hermes/config.yaml
mcp_servers:
  world:
    url: "http://127.0.0.1:8760/mcp/npc/AH-03"
    headers:
      X-NPC-ID: "AH-03"
    supports_parallel_tool_calls: false
```

**方式 B：stdio MCP Server**

每个 Hermes 拉起一个子进程，用环境变量注入身份：
```yaml
mcp_servers:
  world:
    command: "python"
    args: ["-m", "smallville_mcp"]
    env:
      NPC_ID: "AH-03"
      WORLD_BRIDGE_URL: "http://127.0.0.1:8700"
```

### 3.3 MCP 层的内部职责
1. **世界状态镜像**：缓存 UE 推来的最新感知快照，供 `perceive()` 快速返回，避免每次都穿透到 UE
2. **NPC 路由**：根据请求身份，把工具调用转发到正确的 NPC
3. **事件队列**：UE 的异步事件（如"修理厂着火""柚子叫你过去"）暂存，等对应 Agent 下次 `perceive()` 时投递
4. **行动结果回执**：把 UE 的执行结果同步返回给 Agent，让它知道"我的动作成功了没"
5. **动作合法性校验**：过滤非法指令（如去一个不存在的区域），返回错误描述让 Agent 自我纠正

### 3.4 Hermes 自带能力如何映射到斯坦福小镇
好消息是 Hermes 本身就有一部分斯坦福小镇需要的机制，**不用你重复造**：

| 斯坦福小镇机制 | Hermes 对应能力 | 你要补的部分 |
|---|---|---|
| 记忆流 | MEMORY.md + SQLite FTS5 全文检索 | 把感知快照喂进去即可 |
| 反思（高层认知归纳） | GEPA 自进化 + 技能自动沉淀 | 无需额外开发 |
| 记忆检索（三维度评分） | 内置检索机制 | 无需额外开发 |
| 规划（日程生成+动态重排） | 内置 cron + 任务规划 | 用世界时钟触发即可 |
| 感知（局部视野） | ❌ 无 | **必须由 MCP+UE 提供**（本方案核心） |
| 多 Agent 并发与社交 | 部分（子代理是任务导向，非社交） | **MCP 层的 send_message + UE 的听觉感知来补** |

## 四、三维场景下可行吗？

**可行，但有三点必须正视。**

### ✅ 可行的理由
1. **斯坦福小镇本质与渲染无关**：它的"灵魂"是认知循环（感知→记忆→反思→规划→行动），2D 还是 3D 只是**感知快照和行动执行的载体不同**。UE 提供更丰富的感知（空间、朝向、遮挡）和更生动的表现，反而是加分项。
2. **Hermes 已具备记忆/反思/规划**：斯坦福小镇最难的三大件 Hermes 基本内建，你主要工作量在"感知注入 + 行动执行 + 多 Agent 路由"，而不是从零实现认知架构。
3. **MCP 是标准协议**：解耦得干净，UE 和 Hermes 谁都不用改内核，中间层独立演进。

### ⚠️ 必须解决的三个难点

**难点 1：延迟与节奏（最关键）**
- LLM 决策是**秒级**的，UE 是**帧级**的。NPC 不能"卡住不动等 LLM 想完"。
- **解决**：NPC 采用"当前动作持续执行 + 后台异步请求下一个决策"的模式。走路/维修这类动作本身耗时几秒，正好覆盖 LLM 思考时间。用行为树管理"当前动作"，Agent 只负责决定"下一步做什么"。

**难点 2：成本与频率**
- 5 个 Agent 若每秒都调 LLM，token 消耗和费用会失控。
- **解决**：事件驱动而非轮询。只在"感知发生显著变化""当前动作完成""被其他 NPC 搭话"时才触发一次 LLM 决策。空闲时 NPC 走内置的低成本日常循环（沿用规划好的日程），不调 LLM。

**难点 3：多 Agent 社交的因果一致性**
- A 对 B 说话，B 要真的"听到"并可能回应，需要感知和消息在时序上对齐。
- **解决**：MCP 层做一个轻量"世界时间步"仲裁，保证对话事件按序投递；`speak` 的内容通过 UE 听觉感知半径 + MCP 事件队列双通道送达接收方。

### 📊 落地建议路线
1. **先跑通 1 个 NPC**：单个 Hermes + 单个 MCP 端点 + UE 里一个能感知会移动的机器人，验证"感知→决策→行动→再感知"闭环
2. **再上 2 个 NPC 做社交**：验证 `speak` / `send_message` 的双向对话
3. **最后扩到 5 个 + 涌现事件**：植入初始记忆种子（见设定文档），观察是否自发涌现出《运转纪念日》这类事件
4. **性能优化**：接入事件驱动、动作队列、成本监控

---

## 五、一句话总结

- **UE 层**：做世界模拟器——提供**文本化的局部感知**和**可执行的行动接口**，绝不碰决策和记忆。
- **MCP 层**：做翻译官和路由器——把 UE 世界包装成 Hermes 能调用的**标准 MCP 工具**，并按 NPC 身份分发。
- **可行性**：完全可行。Hermes 已内建记忆/反思/规划，斯坦福小镇的认知内核基本现成；你的核心工作量是**感知注入 + 行动执行 + 多 Agent 编排**，真正的技术挑战在**延迟节奏、调用成本、社交时序**这三点上，都有成熟的工程解法。
