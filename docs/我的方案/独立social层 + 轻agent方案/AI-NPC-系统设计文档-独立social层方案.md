# AI NPC 智能体系统 — 设计文档（独立social层方案）

> 版本：v2.0（最终方案）
> 日期：2026-07-15
> 目标：打造一款**易迁移、可复用**的智能 NPC 产品，首站基于部门内部 UE 游戏落地。
> 核心配置：**LLM 主导决策** · **云端服务部署** · **小规模（<50 NPC）**

---

## 0. 方案演进说明

本文档为经过多轮讨论后确定的**最终方案**，相比初版（v1.0）的关键调整：

| 项 | 初版 v1.0 | 最终方案 v2.0 | 原因 |
|----|-----------|--------------|------|
| 通信协议 | 自定义 gRPC + Protobuf | **MCP 协议（含流式扩展）** | 采纳三层方案亮点：标准化、开放、工具即接口 |
| 层次划分 | 引擎适配 / Runtime / Social / Foundation | **MOD / MCP / Agent / Social & World / Foundation** | 融合三层方案的通信骨架 |
| Agent 实现 | 自研完整 Runtime | **自研极薄决策器**（状态全外置） | Social 层剥离后，Agent 退化为无状态决策函数，自研比引入重型框架更简便 |
| 状态归属 | 分散在 Runtime | **全部集中到外置 Social & World 层** | 明确状态归属，Agent 保持薄、无状态、可替换 |
| 感知通道 | gRPC 双向流 | **统一走 MCP 扩展（流式）** | 通道统一，降低复杂度 |
| 群体协作 | 中心化调度器 | **去中心化协商** | 更真实的社区涌现感 |

## 1. 设计目标与核心原则

### 1.1 产品目标
让 AI 同时控制多个 NPC，使其能够：
- **相互交流**：基于自然语言的自主对话。
- **协同工作**：多个 NPC 通过**去中心化协商**围绕共同目标分工协作。
- **社交网络**：NPC 之间存在动态演变的关系（好感、信任、亲疏）。
- **富有生机的社区**：事件传播、群体涌现行为，形成"活着的"世界。

### 1.2 核心设计原则

| 原则 | 说明 | 对迁移/复用的价值 |
|------|------|-------------------|
| **引擎无关** | AI 侧与 UE 完全解耦，MOD 层是唯一引擎耦合点 | 换引擎只重写 MOD 层 |
| **协议标准化（MCP）** | 游戏能力以 MCP Tool 暴露，Agent 通过 MCP 调用 | 任何 MCP-Agent 可即插即用 |
| **状态外置** | 记忆/社交/协作状态全归 Social 层，Agent 无状态 | Agent 可替换、可多实例、易恢复 |
| **Agent 极薄** | Agent 只做"上下文→推理→调工具→输出"决策循环 | 自研成本低、完全可控 |
| **配置即内容** | 人设、关系、规则全部数据化 | 换游戏只改配置 |

> **迁移复用本质**：MOD 层（引擎耦合）+ Agent 层（薄决策器）之外，**Social & World 层与 Foundation 层 100% 跨项目复用**。换引擎只改 MOD 层；换游戏只改配置。

## 3. MOD 层（引擎侧插件）

**定位**：唯一与 UE 耦合的层，作为游戏内插件/MOD 存在。

### 3.1 职责
- **感知采集**：聚合视觉/听觉范围内的实体、空间信息、游戏事件。
- **动作执行**：将 Agent 下发的语义指令翻译为 UE 调用（`MoveToActor` / `PlayMontage` / TTS / 交互）。
- **能力暴露**：将游戏能力封装为 **MCP Tool**（如 `go_to`、`say`、`play_emote`、`interact`、`query_surroundings`）。
- **感知推送**：以 **MCP 流式扩展** 主动、实时推送感知帧。

### 3.2 暴露的 MCP Tool（示例）

| Tool | 参数 | 说明 |
|------|------|------|
| `go_to` | target_id / position | 移动到目标或坐标 |
| `say` | target_id, content, emotion | 说话（引擎负责字幕/TTS） |
| `play_emote` | emote_id | 播放表情/动画 |
| `interact` | object_id, action | 与物体交互 |
| `query_surroundings` | radius | 查询周边实体 |

### 3.3 感知帧结构（经 MCP 流式推送）

```json
{
  "npc_id": "blacksmith_tom",
  "timestamp": 1752566400,
  "self": { "position": [x,y,z], "rotation": [..] },
  "entities": [
    { "id": "baker_anna", "type": "NPC", "distance": 3.2, "tags": {"occupation":"baker"} }
  ],
  "events": [
    { "type": "HEARD_SPEECH", "from": "baker_anna", "content": "早上好，汤姆" }
  ],
  "world": { "time": "08:00", "weather": "sunny" }
}
```

### 3.4 迁移约定
- Agent 侧永远只调用**语义化 MCP Tool**，绝不出现引擎具体 API。
- 迁移到 Unity/其他引擎：**只需重新实现 MOD 层**（暴露相同的 MCP Tool 集 + 感知推送），上层零改动。

---

## 4. MCP 层（无状态桥接）

**定位**：连接引擎与 AI 系统的标准化桥接，**无状态、可水平扩展**。

### 4.1 职责
- **MCP Server/Router**：聚合 MOD 层暴露的所有 Tool，向 Agent 提供统一的工具目录。
- **长连接管理**：维持与游戏引擎的实时长连接，承载 Tool 调用与感知流。
- **双向流转**：
  - 上行：将 MOD 推送的**感知事件流**转发给 Social 层（触发决策）。
  - 下行：将 Agent 的 **Tool 调用**转发给 MOD 层执行。
- **无状态**：本层不保存任何业务状态，仅做路由与协议转换，故障可随时重启/扩容。

### 4.2 统一走 MCP 扩展的说明
- 常规工具调用：标准 MCP `tools/call`。
- 高频感知推送：采用 **MCP 的流式/通知扩展**（如 server-initiated notifications / streaming），使引擎能主动推送感知帧，而非 Agent 轮询。
- **设计权衡**：统一协议降低系统复杂度与心智负担；对感知实时性的要求通过 MCP 流式能力 + 长连接保障。需在 PoC 阶段验证高频推送下的延迟表现，必要时对感知帧做**聚合/降频/显著性过滤**。

## 5. Agent 层（自研极薄决策器）

**定位**：单个 NPC 的"一次性大脑"——**无状态决策函数**。状态全在 Social 层，Agent 只负责"这一刻怎么想、怎么做"。

### 5.1 为什么自研而非用现成框架
由于 Social 层已剥离所有状态，Agent 只需完成一个几百行的决策循环。现成框架（Strands/LangGraph）自带的记忆、状态机、多 Agent 编排等能力**在此架构下全部用不上**，引入反而增加学习、"阉割"内置能力、版本维护等负担。故**自研更简便、更可控**。

### 5.2 Agent 的唯一职责（决策循环）

```
输入（Social 层注入的上下文）
   │
   ▼
① 拼装 prompt（人设 + 关系 + 检索记忆 + 当前感知 + 可用 Tool）
   │
   ▼
② 调用 LLM 推理（经 LiteLLM 网关，模型可路由）
   │
   ▼
③ 调用 MCP Tool（执行动作）
   │
   ▼
④ 输出结构化决策 → 返回 Social 层写回
```

### 5.3 结构化输出契约

```json
{
  "reasoning": "安娜跟我打招呼，她是我的朋友，应该友好回应",
  "actions": [
    { "tool": "say", "args": { "target_id": "baker_anna", "content": "早啊安娜！", "emotion": "friendly" } }
  ],
  "memory_write": "今早安娜主动向我问好",
  "relation_delta": { "target": "baker_anna", "affinity": +0.02 }
}
```

### 5.4 明确的能力边界

| ❌ Agent 不做（归 Social 层） | ✅ Agent 只做 |
|-----------------------------|--------------|
| 长期记忆存储 / 检索排序 | 拼装 prompt |
| 社交关系管理 | 单轮 LLM 推理 |
| 群体协作调度 | 调 MCP Tool |
| 事件传播 | 输出结构化决策 |
| 决定"何时思考"（触发） | 无状态返回 |

### 5.5 技术实现（自研栈）
- **LLM 调用**：`LiteLLM`（多模型路由、限流、重试、降本分级）。
- **工具调用**：MCP 官方 Client SDK。
- **输出校验**：JSON Schema 校验 + 失败重试（保证结构化输出稳定）。
- **形态**：无状态服务，每个 NPC 决策请求独立处理，支持多实例并发（<50 规模轻量）。

## 6. Social & World 层（外置状态核心 · 差异化核心）

**定位**：整套系统的**灵魂**。Agent 越薄，本层越重。承载所有"群体智慧"与状态。

### 6.1 五大子模块

```
┌──────────────────────────────────────────────────┐
│              Social & World 层                     │
│  ① 记忆管理   ② 社交网络图   ③ 上下文组装           │
│  ④ 事件总线/传播   ⑤ 去中心化协作协商   (+世界状态)  │
└──────────────────────────────────────────────────┘
```

### 6.2 ① 记忆管理（分层记忆流）

| 层级 | 存储 | 说明 |
|------|------|------|
| 工作记忆 | Redis | 当前对话/任务上下文 |
| 情节记忆 | Qdrant | 发生过的事件流 |
| 语义记忆 | Qdrant | 对世界/他人的认知 |
| 反思记忆 | PostgreSQL | 周期性总结提炼的高层认知 |

- **检索打分**：`score = α·相关性(向量相似) + β·时近性(时间衰减) + γ·重要性(LLM打分)`，取 top-k 注入。
- **反思机制**：累计重要性超阈值时，触发 LLM 总结近期记忆 → 写回反思记忆 → 影响社交图。

### 6.3 ② 社交网络图
- **结构**：有向带权图。节点=NPC/玩家，边=关系。
- **边属性**：`affinity(好感)` / `trust(信任)` / `familiarity(熟悉度)` / `relation_type`。
- **演化**：每次交互后按规则 + Agent 返回的 `relation_delta` 更新权重。
- **存储**：<50 规模用 **PostgreSQL 关系表** 即可（规模上量再迁 Neo4j）。

### 6.4 ③ 上下文组装（与 Agent 的接口）
Social 层负责把以下内容组装成 prompt 注入 Agent：
```
[人设 Persona] + [与相关对象的社交关系] + [检索到的 top-k 记忆]
+ [当前感知观察] + [可用 MCP Tool 列表]
```
> 这是 Social 层与 Agent 层之间**唯一的接口契约**。Agent 拿到的已是"精选好的上下文"。

### 6.5 ④ 事件总线 / 信息传播
- **实现**：Redis Streams（发布/订阅）。
- **八卦机制**：事件**不瞬时全知**，而是通过 NPC 间对话逐步扩散，制造真实的信息差与滞后。
- **触发决策**：感知事件流经此总线，触发相关 NPC 的决策。

### 6.6 ⑤ 去中心化协作协商
**采用去中心化协商模型**（而非中心化调度器）：
- 无中央调度者。NPC 通过**相互对话/消息**表达意图、协商分工。
- 每个 NPC 基于自身人设、能力、关系与当前目标，**自主决定是否参与、承担何种角色**。
- 通过**共享黑板（Blackboard）**同步协作进度（存于 Redis）。
- **优势**：涌现感强、更真实、无单点瓶颈。
- **风险与应对**：协商可能不收敛或低效 → 引入**超时兜底**、**协商轮次上限**、以及可选的"软引导"（世界规则/事件推动），并在可观测性中重点监控协作链路。

### 6.7 世界状态
- 全局客观事实库：游戏内时间、天气、公共事件、地点信息。
- 与各 NPC 的主观记忆区分开（客观现实 vs 主观认知）。

### 6.8 开发难度说明
- 🟢 低（标准工程）：记忆存储、社交图 CRUD、上下文组装、世界状态。
- 🟡 中（需调优）：记忆检索打分、关系演化规则、事件传播规则。
- 🔴 高（核心难点）：**去中心化协作协商的收敛性** 与 **涌现行为可控性**——建议延后到后期阶段攻坚，前期可先用简化协商规则。

## 7. Foundation 基础服务层

| 模块 | 选型 | 职责 |
|------|------|------|
| LLM 网关 | **LiteLLM** | 多模型路由、限流、重试、降级、成本核算、分级路由降本 |
| 向量数据库 | **Qdrant** | 情节/语义记忆的相似度检索 |
| 缓存/状态/总线 | **Redis** | 工作记忆、协作黑板、事件总线(Streams)、决策缓存 |
| 持久化存储 | **PostgreSQL** | 社交图、反思记忆、配置、对话历史 |
| 可观测性 | **OpenTelemetry + Langfuse + Grafana** | 追踪每个 NPC 的决策链路、协作链路、token/延迟 |

## 8. 技术选型总览

| 层 / 模块 | 选型 | 理由 |
|-----------|------|------|
| MOD 层 | UE C++ 插件（暴露 MCP Tool） | 贴合引擎原生开发 |
| 通信协议 | **MCP（含流式扩展）+ 长连接** | 标准化、开放、工具即接口 |
| MCP 层 | MCP Server/Router（无状态服务） | 水平扩展、故障隔离 |
| Agent 层 | **自研（Python）** + LiteLLM + MCP Client SDK | 薄决策器，自研最简便可控 |
| LLM | 多模型可切换 + 分级路由（闲聊小模型 / 复杂决策大模型） | 控成本、保智能感、易迁移 |
| Social 层 | Python 服务 + Qdrant + Redis + PG | 差异化核心，标准工程栈 |
| 部署 | Docker + Kubernetes（单区域集群，<50 NPC） | 云端弹性伸缩 |

## 9. 关键数据流：一次完整决策

```
① 引擎产生感知（安娜向汤姆问好）
        │  MOD 层采集，MCP 流式推送
        ▼
② MCP 层转发感知事件 → Social 层
        │
        ▼
③ Social 层：事件总线触发汤姆决策
        · 检索汤姆的相关记忆（与安娜的过往）
        · 查询社交图（汤姆↔安娜：朋友, 好感0.7）
        · 组装上下文
        │  注入
        ▼
④ Agent 层（汤姆实例）：LLM 推理
        · 输出：{say "早啊安娜！", memory_write, relation_delta+0.02}
        │  调 MCP Tool `say`
        ▼
⑤ MCP 层转发 `say` → MOD 层 → 引擎播放对白/TTS
        │
        ▼
⑥ Social 层写回：存记忆、更新社交图(好感+0.02)、广播事件（可能被旁人听到）
```

## 10. 迁移复用策略

### 10.1 迁移到新引擎
1. 用目标引擎实现 MOD 层（暴露相同 MCP Tool 集 + 感知推送）。
2. 接入 MCP 层。
3. **完成——MCP/Agent/Social/Foundation 全部零改动**。

### 10.2 迁移到新游戏（同引擎）
1. 编写新 NPC 配置（人设/关系/技能）。
2. 配置世界规则与事件类型。
3. **完成——核心代码零改动**。

### 10.3 复用性度量（验收标准）
- 换引擎：改动仅限 MOD 层。
- 换游戏：核心代码零改动，仅改配置。
- Agent 可平滑替换：因无状态、状态全在 Social 层。

## 11. 分阶段落地路线

| 阶段 | 目标 | 关键交付 |
|------|------|----------|
| **P0 骨架** | 打通 引擎↔MCP↔Agent 通路 | UE MOD 插件(MCP Tool) + MCP 层 + 单 NPC 薄 Agent 闭环 |
| **P1 单体智能** | 单 NPC 记忆 + 自然对话 | Social 层记忆模块 + 上下文组装 + 可观测性 |
| **P2 社交涌现** | 多 NPC 交流 + 关系演化 | 社交图 + 事件总线/传播 + NPC 间自主对话 |
| **P3 群体协作** | 去中心化协商协同 | 协商机制 + 共享黑板 + 反思机制 |
| **P4 产品化** | 易迁移复用工具链 | 配置工具 + 调试面板 + 迁移文档 + MOD SDK |

---

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| MCP 流式高频感知延迟 | 反应慢 | 感知聚合/降频/显著性过滤；PoC 验证延迟 |
| 去中心化协商不收敛 | 协作失败/低效 | 超时兜底 + 轮次上限 + 世界规则软引导 |
| 涌现行为失序 | 负面群体行为 | 世界规则约束 + 事件审计 + 可干预机制 |
| LLM 成本/延迟 | 商业性/体验 | 分级路由 + 决策缓存 + NPC 休眠 + 决策分层 |
| LLM 幻觉/越界 | 不合理动作 | 结构化输出 + Tool 白名单校验 + 护栏 |
| 引擎耦合渗透 | 破坏迁移性 | 严守 MCP 边界，评审拦截引擎 API 泄漏到上层 |

---

## 13. 总结

本方案以 **"MCP 标准桥接 + 极薄无状态 Agent + 外置 Social & World 层"** 为核心：

- **易迁移**：换引擎只改 MOD 层；换游戏只改配置。
- **可复用**：MCP/Agent/Social/Foundation 跨项目复用。
- **开发经济**：Agent 自研极薄（省框架负担），大量借力现成组件（LiteLLM/Qdrant/Redis/PG）。
- **富有生机**：分层记忆 + 社交网络图 + 事件传播 + 去中心化协商，构建自主演化的 NPC 社区。
- **贴合现状**：LLM 主导、云端部署、小规模优化，首站高效落地 UE 游戏。

**下一步建议**：从 **P0 骨架**入手——先让 UE MOD 层暴露少量 MCP Tool、跑通单 NPC 的"感知→决策→动作"闭环，验证 MCP 流式感知的实时性后，再逐步叠加 Social 层的记忆、社交与协作能力。
