# 记忆系统设计方案 —— UE 零记忆 / MCP 零状态约束下的实现

> 前置约束（不可协商）：
> - **UE 层**只做游戏端内容——仅提供感知、行动、查询接口，不存任何记忆/认知产物。
> - **MCP 层**只做桥接——协议转换 + 路由，不做任何缓存或二次存储（沿用 SmartNPC 星露谷版已验证的边界：`smartnpc-mcp` 禁止持久化业务状态）。
> - 记忆系统的**全部重量压在 Hermes Agent 一侧**：会话上下文 + `MEMORY.md`。
>
> 本方案回答：在这个更严格的边界下，斯坦福小镇的「观察-评分-检索-反思-规划」认知循环能做到什么程度、如何尽可能贴近原版效果、差距在哪里不回避。

---

## 一、边界重申：为什么 UE 和 MCP 都不能存状态

### 为什么 MCP 不能存状态

一旦 MCP 自己也存一份"当前记忆/计划"，就会出现 **UE 状态、MCP 内存、Hermes MEMORY.md 三份拷贝互相不同步**的风险，5 个 Agent 并发运转时几乎必然出现不一致。此外：

- **MCP 进程重启不能牵连认知状态**：开发期 MCP 会频繁重启/崩溃重连，如果记忆或计划的权威副本挂在 MCP 内存里，一次重启就让 5 个 NPC 的记忆全部清零。
- **职责边界清晰、可独立测试**：三层各自单一职责（UE=物理世界真相，MCP=无状态转发，Hermes=认知与记忆），任何一层都可以独立重启、独立单测，不需要跨层协调状态。

### 为什么 UE 也不能存记忆

"计划""认知产物"本质是认知层的东西，不是物理世界状态——不应该像电量、位置那样挂在 UE 的 NPC 数据上。UE 只暴露 `perceive()` / `move_to()` / `interact()` 这类物理世界读写，认知层的一切（记忆、计划、反思）完全交给 Hermes 自己承载。

### 结论

记忆系统必须是一个**纯 Hermes 侧方案**——不需要在 UE 或 MCP 加一行存储代码，只靠 **Hermes 会话上下文 + `MEMORY.md` 的格式设计 + cron 调度 + skill/prompt 约定**来实现。

---

## 二、Hermes 原生能力盘点：地基与差距

Smallville 论文的记忆流本质是四件事：**记录观察 → 评分重要性 → 按需检索 → 定期反思生成高层认知**。Hermes 已经提供了地基，但和原版有本质差距，必须先说清楚：

| Smallville 机制 | Hermes 原生能力 | 差距 |
|---|---|---|
| **观察记录**（每次感知都存一条节点） | 无自动机制，需显式调工具写 `MEMORY.md` | 需要自己设计"什么值得写"的策略（否则会把 `MEMORY.md` 撑爆） |
| **重要性评分**（LLM 对每条记忆打 1-10 分） | 无内建评分器 | 需要靠 prompt 约定让 Hermes 自己在写入时打分 |
| **检索**（时效性+重要性+关联度三维度，关联度基于 embedding 语义相似度） | SQLite **FTS5 全文检索**（关键词匹配） | **本质差距**：FTS5 是词匹配，不是语义相似度。检索质量天花板比原版低 |
| **反思**（记忆重要性累计超阈值 → LLM 归纳高层认知） | GEPA 自进化（跨大量 episode 优化 prompt/skill） | GEPA 解决的是"如何把任务做得更好"，不是"从具体记忆中提炼人生感悟"——目标不同，不能直接当反思用 |
| **计划**（每天生成，本质也是认知产物） | 会话上下文天然记得自己刚生成的计划 | 会话若中途重启（gateway 崩溃/重连），当天计划会丢失，只能回退到昨晚 `MEMORY.md` 的摘要 |

**结论**：Hermes 给的是"持久化存储 + 关键词检索"这个地基，四层机制里最难的"语义检索"和"反思触发"必须自己在 prompt/skill 层面搭。

## 三、具体实现方案（纯 Hermes 侧，零 UE/MCP 改动）

### 3.1 观察记录 —— 选择性写入，代替 Smallville 的全量记录

Smallville 原版记录密度极高（NPC 做任何事都生成一条记忆节点，靠检索时的评分过滤噪音）。这套模式**在 `MEMORY.md` 上直接照搬会失败**——全文本文件塞满琐碎细节，之后每次系统提示都要载入，既贵又稀释信号。

采用**带评分的三段式判断**，每次 `perceive()` 之后、决策前过一遍：

```
1. 这次感知有没有"新信息"（不是重复上次已知的状态）?
2. 用一句话估计重要性 1-10（路人闲聊=2，和老修吵架=8，发现涌现事件线索=9）
3. 重要性 ≥ 阈值（建议 5）才调用记忆写入工具；低于阈值只留在本轮会话上下文里，
   自然随对话轮次淡出
```

这是把 Smallville"先全存后过滤"的模式，改成"先评分后决定存不存"，在 `MEMORY.md` 体量和检索精度之间找平衡——是本约束下唯一可行的路。

### 3.2 检索 —— 结构化关键词，缓解语义检索的缺失

FTS5 是词匹配，没法理解"站长和老修聊了很久"和"站长向老修倾诉"是同义。缓解办法是**把记忆写成结构化、关键词密度高的格式**，而不是流畅的自然语言叙述：

```markdown
Day12 14:20 [人物:老修][地点:修理间][主题:私藏旧核心][重要性:8]
老修在诊断椅上被站长撞见对着旧核心自言自语，慌忙掩饰。
```

固定 `[人物][地点][主题][重要性]` 标签位，检索时用这些标签词做关键词命中，比自然语言段落检索命中率高得多。这是纯 prompt/格式约定，不需要任何额外基础设施。

### 3.3 反思 —— 用 Hermes Cron 显式模拟 Smallville 的反思触发

GEPA 不能替代反思，但 Hermes 的 **cron 调度**天然可以拿来手搓一个反思触发器，完全在 Hermes 侧闭环：

```yaml
# 每个 NPC profile 的 cron 配置，建议每天日终触发一次
cron:
  - rrule: "..."   # 对应"日终"时间点
    prompt: |
      回顾今天 MEMORY.md 里新增的记忆条目，如果其中出现了重复模式或值得
      升华的认知（例如"每次电工提加电申请我都下意识想拒绝"），提炼成一条
      更高层的认知记忆，单独标记 [反思] 写入 MEMORY.md。如果今天没有值得
      反思的内容，跳过不写。
```

这与 Smallville 原版"重要性累计超阈值触发反思"的机制不完全一样（原版是阈值触发，这里是定时触发），但效果类似——**用"日终固定触发"替代"重要性累计阈值触发"**，实现成本低很多，且完全不需要 MCP/UE 参与计数。

如果想更贴近原版，可以让 Hermes 自己在每次写入记忆时于末尾追加"累计重要性: N"，cron prompt 里加一句"如果累计重要性超过 30 再触发反思"，让 LLM 自己读文件里的数字做判断——不需要外部计数器，判断逻辑完全内嵌在 markdown 文本和 prompt 里。

### 3.4 计划 —— 完全收归会话上下文 + `MEMORY.md` 定点覆盖区

"计划"是认知产物，不该塞进 UE 的 NPC 状态字段（UE 只暴露物理世界状态：位置/电量/损耗）。

**方案**：计划只活在 Hermes 会话上下文里（Hermes 自己刚生成的东西，天然记得），`MEMORY.md` 开一个专门的**覆盖式**（非追加式）区块做崩溃恢复：

```markdown
## 当前计划（每次 update 覆盖，非追加）
09:00 仓库整理旧核心架
09:30 去修理间看看老修的零件短缺
10:30 ...
```

每次计划变更时，Hermes 用工具把这个区块**整体替换**（不是 append），避免 `MEMORY.md` 被计划修订记录刷屏。

**代价（不回避）**：如果 Hermes 会话中途崩溃重连，新会话只能读到"最后一次覆盖时"的计划快照，不会丢失但可能有几分钟延迟——这是严格无状态换来的可接受代价。

## 四、跟斯坦福小镇原版的真实差距（不回避）

| 维度 | Smallville 原版 | 本方案上限 | 差距性质 |
|---|---|---|---|
| 记忆密度 | 事无巨细全记录，靠检索过滤 | 主动筛选后才写入 | **信息保真度较低**——被判定"不重要"的细节，原版还能在事后被重新评估重要性，本方案一旦不写就永久丢失 |
| 检索精度 | embedding 语义相似度 | 关键词全文检索 + 结构化标签缓解 | **检索到"相关但字面不同"记忆的能力弱**，依赖写入时的关键词规范性 |
| 反思机制 | 重要性累计阈值自动触发，LLM 生成抽象认知节点 | cron 定时触发 + prompt 引导归纳 | 效果接近，但触发时机是"日终"而非"信息量到了就触发"，少了原版那种"关键时刻突然开悟"的即时性 |
| 计划实时性 | 内存态，任何时候都是最新 | 崩溃后有秒级到分钟级恢复延迟 | 工程妥协，正常运行时无感 |

## 五、结论与后续演进路径

在"UE 零记忆、MCP 零状态"这条严格边界下，记忆系统能做到 **"结构相似，精度打折"**——观察/评分/检索/反思/计划这五个动作全部可以用纯 Hermes 侧手段（skill 约定 + cron + `MEMORY.md` 格式设计）实现闭环，不需要在 UE 或 MCP 加一行存储代码。

真正拉开差距的是**检索精度**（关键词匹配 vs 语义相似度）——这是 Hermes 内建能力的硬上限。如果后续想突破，唯一的路径是给 Hermes 接一个外部向量检索工具（仍可以设计成 Hermes 自己调用的 MCP 工具，由 Hermes 自己的记忆插件调用一个无状态的 embedding 计算服务，而不是让 MCP 缓存向量库）——但这已超出"最小化改动"的范围，建议先用关键词+标签方案跑通效果，如果实测检索命中率不够再考虑加这一层。
